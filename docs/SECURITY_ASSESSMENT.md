## 1. الملخص التنفيذي (Executive Summary)

أُجري هذا التقييم الأمني الشامل لفحص جاهزية تطبيق **مُرافق (Murafiq)** — المبني بتقنيات React 19 و TypeScript و Firebase Firestore — فيما يخص المصادقة (Authentication)، التفويض وصلاحيات الوصول (Authorization)، عزل بيانات المستخدمين (Tenant Data Isolation)، ومخاطر التهيئة التلقائية للبيانات النموذجية (Sample Data Seeding).

### النتيجة الإجمالية (Key Finding):
يعمل النموذج الحالي للتطبيق بنمط **مستأجر عام مشترك غير محمي (Public Multi-Tenant Shared Store)**، حيث تُخزّن جميع سجلات العملاء، ومحاضر الاجتماعات، والمهام السرية، والأسعار المتفاوض عليها في مجموعات جذرية عامة (`/clients`، `/meetings`، `/tasks`، `/notes`) دون أي ربط بحساب المستخدم (`userId`)، ودون تفعيل للمصادقة في دورة حياة التطبيق، مع وجود قواعد أمان تسمح بالقراءة والإدراج والتعديل والحذف لأي زائر مجهول (`allow list: if true;`).

يوثّق هذا التقرير الثغرات المؤكدة بدقة مع أرقام الأسطر والملفات المتأثرة، ويضع خطة معمارية محكمة للانتقال إلى **بنية بيانات معزولة لكل مستخدم (Per-User Scoped Architecture)** مع استراتيجية ترحيل آمنة للبيانات الحالية والحفاظ التام على ميزة العمل دون اتصال (Offline-First).

- **في `src/services/firebase.ts`:**
  - يتم استيراد `getAuth` وتهيئة الكائن في السطر 24: `export const auth = getAuth(app);`.
  - لا يتم استخدام كائن `auth` إلا في دالة تسجيل الأخطاء `handleFirestoreError` (الأسطر 56–65) لاستخراج `auth.currentUser?.uid` إن وجد.

- **في `src/App.tsx`:**
  - يبدأ التطبيق بالاشتراك الفوري في Firestore عند أول تحميل (الأسطر 70–126 عبر `useEffect`) دون التحقق مما إذا كان هناك مستخدم مسجل الدخول أم لا.

## 5. مخاطر زرع البيانات التجريبية التلقائي (Risks of Automatic Sample-Data Seeding)

في `src/App.tsx` الأسطر 85–88:
```typescript
if (data.length > 0) {
  setClients(data);
} else {
  // Seed database with authentic initial Arabic data if completely empty
  seedInitialData(INITIAL_CLIENTS, INITIAL_MEETINGS, INITIAL_TASKS, INITIAL_NOTES);
}
```

### المخاطر البرمجية والتشغيلية المترتبة:
1. **حالة السباق عند بدء التشغيل (Race Condition on First Load):** إذا فتح مستخدمان التطبيق في نفس اللحظة وقاعدة البيانات فارغة، سيطلق كلاهما طلب `writeBatch` لكتابة نفس المعرفات، مما يولد تضارباً واستهلاكاً غير مبرر لعمليات الكتابة.
2. **استحالة الحذف التام (Resurrection of Deleted Data):** إذا قرر مستخدم حذف جميع عملائه لإنشاء سجلات حقيقية، فبمجرد وصول عدد العملاء إلى `0`، سيفسر التطبيق ذلك بأنه "قاعدة بيانات فارغة جديدة" ويعيد زرع البيانات التجريبية فوراً!
3. **خلط البيانات الحقيقية بالوهمية:** تظهر أسماء العملاء الوهميين (مثل "م. أحمد الجاسم" و"د. خالد العمري") في شاشات مستخدمين حقيقيين، مما يهدد مصداقية التطبيق المهنية.

## 6. الهيكلية المقترحة لعزل بيانات المستخدمين (Proposed Per-User Architecture)

لتحقيق العزل التام للبيانات (True Tenant Isolation)، تمت المقارنة بين خيارين معماريين:

### المقارنة المعمارية:

| وجه المقارنة | الخيار أ: المجموعات الفرعية تحت المستخدم (الموصى به)<br>`/users/{userId}/...` | الخيار ب: مجموعات جذرية مع حقل `userId`<br>`/clients` with `userId` filter |
|:---|:---|:---|
| **الأمان البنيوي** | **أعلى درجة أمان:** يتم العزل على مستوى المسار (Path-level Security). القواعد بسيطة ومستحيلة التسريب. | **معرض للأخطاء:** أي استعلام ينسى شرط `where('userId', '==', uid)` يرفضه المحرك بالكامل أو يسرب البيانات إن كانت القواعد رخوة. |
| **قواعد الأمان (Firestore Rules)** | واضحة ومباشرة: لا تتطلب قراءة المستند للتحقق من المالك لأن المعرف في الرابط `{userId}`. | تتطلب فحص حقل المستند الداخلي `resource.data.userId`، وتتطلب فحص `request.resource.data.userId` في الإنشاء. |
| **الفهارس المركبة (Composite Indexes)** | فهارس محلية تلقائية داخل كل مستخدم دون تضخم عالمي. | تتطلب فهارس مركبة عالمية معقدة لكل حقل مضاف إليه `userId`. |
| **حذف حساب المستخدم (GDPR / Right to be Forgotten)** | حذف مجلد المستخدم ومجموعاته الفرعية دفعة واحدة بنظافة. | يتطلب استعلامات بحث وحذف متفرقة عبر 4 مجموعات مختلفة. |

### الهيكلية المعتمدة للمسارات (Recommended Firestore Document Hierarchy):

```
/users/{userId}                         [مستند المستخدم الأساسي]
    │
    ├── /clients/{clientId}             [عملاء هذا المستخدم فقط]
    │
    ├── /meetings/{meetingId}           [لقاءات ومحاضر هذا المستخدم فقط]
    │
    ├── /tasks/{taskId}                 [مهام والتزامات هذا المستخدم فقط]
    │
    └── /notes/{noteId}                 [ملاحظات هذا المستخدم فقط]
```

### تعديل الموديل البرمجي في TypeScript (`src/types/index.ts`):
إضافة حقل `userId: string` الإلزامي في كافة الكيانات:
```typescript
export interface Client {
  id: string;
  userId: string; // معرف المستخدم المالك
  name: string;
  company?: string;
  phone?: string;
  email?: string;
  notes?: string;
  avatarPath?: string;
  color?: string;
  isFavorite?: boolean;

  updatedAt: string;

```
*(وكذلك لـ `Meeting` و `ActionItem` و `Note`).*

### مزايا هذا النموذج:
1. **الدخول الفوري بدون احتكاك (Zero-friction Guest Access):** عبر `signInAnonymously()`، يستطيع المستقل استخدام التطبيق فوراً بدون شاشة تسجيل معقدة، ويحصل على معرّف مشفر معزول في Firestore.
2. **الترقية السلسة للحساب الدائم (Account Linking):** متى ما رغب المستخدم في مزامنة بياناته بين أجهزته، يقوم بربط حسابه المؤقت بـ Google أو البريد الإلكتروني وكلمة المرور عبر `linkWithCredential()` دون فقدان أي عميل أو اجتماع أنشأه مسبقاً.
3. **أمان تام لمستمعات البيانات:** لا يبدأ أي اشتراك سحابي في `App.tsx` إلا بعد اكتمال حدث `onAuthStateChanged` وتأكيد وجود `user.uid`.

## 8. الأثر على العمل دون اتصال (Offline-First Impact) والسجلات الحالية

### 8.1 الأثر على العمل دون اتصال (Offline-First):
- **إيجابي ومحمي:** يدعم Firebase Firestore التخزين المحلي التلقائي عبر IndexedDB. بتطبيق المسارات المعزولة `/users/{userId}/...`، يصبح التخزين المحلي في متصفح المستخدم مقتصراً على بياناته فقط، مما يمنع تسريب البيانات عند فتح التطبيق من أجهزة مشتركة.
- منطق حل التعارضات المحلي في `src/utils/conflictLogic.ts` وخوارزميات تصنيف المهام والأجندة في `src/utils/logic.ts` تعمل كدوال نقية (Pure Functions) مستقلة عن طبقة الشبكة، وبالتالي لن تتأثر بنيتها الرياضية إطلاقاً.

### 8.2 الأثر على السجلات الحالية في قاعدة البيانات:
- تحتوي قاعدة بيانات Firestore الحالية (`ai-studio-murafiq-cb988db3-5a07-40b7-b1ca-8eaaae894475`) على سجلات تجريبية في المجموعات الجذرية (`clients/`, `meetings/`, `tasks/`, `notes/`).
- بمجرد فرض قواعد أمان تشترط `request.auth != null && request.auth.uid == userId`، ستصبح المجموعات الجذرية القديمة غير قابلة للوصول بواسطة الواجهة الأمامية للحفاظ على الأمان.

### 8.3 استراتيجية الترحيل الآمن (Safe Migration Strategy):
1. **المرحلة الأولى (عدم التدمير):** الإبقاء على المستندات القديمة في المجموعات الجذرية كنسخة احتياطية وأرشيفية دون حذفها.
2. **المرحلة الثانية (سكربت ترحيل اختياري Idempotent Migration):**
   - للمستخدم المسؤول أو البيئة التجريبية الحالية، يمكن تشغيل دالة ترحيل لمرة واحدة تنقل المستندات الحالية إلى مجلد المستخدم المعتمد:
     `/users/{OWNER_USER_ID}/clients/{clientId}` مع وسم كل مستند بـ `migratedAt: timestamp`.
3. **المرحلة الثالثة (فصل زرع البيانات عن مسار الإنتاج):**
   - جعل زرع البيانات التجريبية إجراءً يدوياً يختاره المستخدم صراحةً من واجهة الإعدادات ("إضافة بيانات تجريبية لحسابي") لملء مساره الخاص `/users/{userId}/...` فقط، بدلاً من حقنها تلقائياً على مستوى النظام بأكمله.

## 9. خطة تنفيذ قواعد الأمان الجديدة (Security Rules Implementation Blueprint)

نموذج القواعد الآمن الموصى بنشره في `firestore.rules` في المرحلة القادمة:

```javascript
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    // 1. الإغلاق التلقائي لجميع المسارات غير المعرفة
    match /{document=**} {
      allow read, write: if false;
    }

    // دوال المساعدة العالمية
    function isSignedIn() {
      return request.auth != null;
    }

    function isOwner(userId) {
      return isSignedIn() && request.auth.uid == userId;
    }

    function isValidId(id) {
      return id is string && id.size() > 0 && id.size() <= 128 && id.matches('^[a-zA-Z0-9_\\-]+$');
    }

    // ملف فحص الاتصال العام فقط
    match /test/{docId} {
      allow read: if true;
    }

    // 2. نطاق بيانات المستخدم المعزولة بالكامل
    match /users/{userId} {
      allow get, update: if isOwner(userId);
      allow create: if isOwner(userId);

      // مجموعات العملاء المعزولة
      match /clients/{clientId} {
        allow read, write: if isOwner(userId) && isValidId(clientId);
      }

      // مجموعات اللقاءات المعزولة
      match /meetings/{meetingId} {
        allow read, write: if isOwner(userId) && isValidId(meetingId);
      }

      // مجموعات المهام المعزولة
      match /tasks/{taskId} {
        allow read, write: if isOwner(userId) && isValidId(taskId);
      }

      // مجموعات الملاحظات المعزولة
      match /notes/{noteId} {
        allow read, write: if isOwner(userId) && isValidId(noteId);
      }
    }
  }
}
```

## 10. معايير الاختبار والقبول (Testing & Acceptance Criteria)

عند البدء بتطبيق الحل الأمني، يجب التحقق من المعايير التالية لضمان نجاح التحول:

1. **اختبار عزل المستأجرين (Tenant Isolation Test):**
   - تسجيل الدخول بالمستخدم (أ) وإنشاء عميل "مؤسسة الرواد".
   - فتح جلسة تصفح خفي وتسجيل الدخول بالمستخدم (ب).
   - **معيار القبول:** لا يظهر عميل المستخدم (أ) في شاشة المستخدم (ب) إطلاقاً، وتعود الاستعلامات بـ `0` نتائج للمستخدم (ب).
2. **اختبار محاولة الاختراق والوصول المباشر (Direct Access Exploit Test):**
   - محاولة إجراء قراءة أو كتابة عبر Firestore SDK إلى مسار مستخدم آخر `/users/{UserA_UID}/clients/...` باستخدام جلسة المستخدم (ب).
   - **معيار القبول:** رفض الطلب فوراً بخطأ `PERMISSION_DENIED` من محرك قواعد الأمان.
3. **اختبار العمل دون اتصال (Offline Resilience Test):**
   - قطع اتصال الشبكة، إنشاء لقاء ومهمة جديدة للمستخدم المصادق.
   - إعادة الاتصال.
   - **معيار القبول:** مزامنة المستندات بنجاح إلى `/users/{uid}/meetings` دون فقدان أو تعارض زائف.
4. **اختبار عدم حقن البيانات التلقائي (Zero Auto-Seeding Test):**
   - إنشاء حساب مستخدم جديد وفارغ.
   - **معيار القبول:** يرى المستخدم شاشات فارغة نظيفة ومرتبة تشجعه على البدء بدلاً من رؤية بيانات نموذجية محقونة في حسابه.

## 11. القرارات المفتوحة التي تتطلب موافقة مالك المنتج (Open Decisions for Product Owner)

نرفع لمالك المنتج القرارات التالية لاعتمادها قبل مرحلة التطوير البرمجي:

1. **مزودو المصادقة المستهدفون (Authentication Providers):**
   - *الخيار الموصى به:* البدء بـ **Google OAuth** + **حسابات الزوار المجهولة (Anonymous Auth)** لتوفير تجربة فورية بدون كلمة مرور، مع إتاحة البريد وكلمة المرور لاحقاً.
2. **مصير السجلات الحالية في قاعدة البيانات التجريبية:**
   - هل يتم ترحيلها إلى حساب مالك المشروع (`majid.khaireddin@gmail.com`) أم أرشفتها والبدء بقاعدة بيانات جديدة كلياً؟
3. **مصير القفل البيومتري المحلي (Local PIN Lock):**
   - هل يُحتفظ به كطبقة حماية ثانوية محلية للشاشة (App Screen Lock) بعد تسجيل الدخول الأساسي بحساب المستخدم، أم يتم استبداله بالكامل بجلسة المستخدم؟ *(التوصية: الإبقاء عليه كطبقة خصوصية عند إعارة الهاتف للغير).*
